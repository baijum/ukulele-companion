Architecture Overview

Three layers, two platforms, one shared core

Here is the 30,000-foot view. A shared Kotlin Multiplatform module sits at the centre. It contains all the domain logic — chord detection, pitch detection, music theory, data models. Below it, two platform-specific apps: Android with Jetpack Compose, iOS with SwiftUI. The shared module has zero platform imports — it is pure Kotlin.

Deep Dive: Chord Detection

How does tap-to-chord work?

  1. User taps fret positions → list of pitch classes (0–11)
  2. Remove duplicates
  3. For each pitch class as candidate root, compute intervals:
    interval = (pc - root + 12) % 12
  4. Match interval set against 20 chord formulas
  5. First match wins (triads prioritized); alternates collected
Let me walk through the chord detection algorithm. It is elegant in its simplicity. When you tap frets, the app gets a list of pitch class integers — 0 for C, 1 for C sharp, up to 11 for B. It removes duplicates, then tries every note as a potential root. For each candidate root, it computes the intervals using modular arithmetic. Then it checks if that set of intervals matches any known chord formula.

Chord Formulas: Music Theory as Data

data class ChordFormula(
    val symbol: String,      // "m", "7", "dim"
    val quality: String,     // "Minor", "Dominant 7th"
    val intervals: Set<Int>, // {0, 3, 7} for minor
    val aliases: List<String> // ["min", "-"]
)

// Detection is just a set comparison:
if (intervals == formula.intervals) {
    matches.add(candidateRoot to formula)
}

The chord formulas are pure data. A major chord is the set {0, 4, 7} — root, major third, perfect fifth. The detection is just a set comparison. This makes it trivially testable and extendable — to add a new chord type, you add one data entry.

Deep Dive: YIN Pitch Detection

From sound waves to note names

Mic 44.1kHz PCM → Silence Gate → Difference Function (FFT)
↓
CMND Normalization → Threshold Search → Confidence Gate
↓
Best Local Estimate → Parabolic Interpolation → Frequency (Hz)

YIN algorithm (de Cheveigné & Kawahara, 2002) — pure Kotlin, no external dependencies

The tuner uses the YIN algorithm, published in 2002. I implemented it in pure Kotlin — no native DSP libraries. The pipeline has 7 steps. Audio comes in at 44.1 kHz in 4096-sample frames. A silence gate checks RMS amplitude. Then the difference function is computed using FFT for O(N log N) performance. CMND smooths the result. A threshold search finds the first dip below 0.15. Confidence gate rejects noisy frames. Then parabolic interpolation refines the lag, which is converted to a frequency.

YIN: The Key Insight

Slide the signal against itself at different offsets (lags).
At the lag matching the signal's period, the difference is minimal. 
// Difference function: d(tau) = sum of (x[j] - x[j+tau])^2
// Decomposed as:  d(tau) = E0 + E(tau) - 2*r(tau)
// where r(tau) = cross-correlation via FFT  -->  O(N log N)

val frequency = sampleRate.toDouble() / refinedTau
  • Frame size: 4096 samples (~93 ms at 44.1 kHz)
  • Hop size: 1024 samples → ~43 updates/sec
  • Range: 65–1100 Hz (covers all ukulele tunings)
The intuition is simple. You slide the signal against itself at different offsets. At the lag that matches the signal's period, the difference is minimal. Divide the sample rate by the lag and you get the frequency. The clever part is using FFT to compute this in O(N log N) instead of the naive quadratic approach.

YIN is great but has limitations — octave errors on low strings, degradation in noise. So I added a neural supervisor. SwiftF0 runs every 5th frame, about every 100 ms. YIN still drives the needle on every frame for low-latency response. When they agree, trust YIN for precision. If they disagree by an octave, trust the neural model.

Chromagram: Audio Chord Detection

From FFT to chord recognition

  1. FFT magnitude spectrum (4096 bins)
  2. Map each bin to a pitch class:
    round(12 * log2(freq / C0)) mod 12
  3. Accumulate energy into 12 chroma bins
  4. Normalize so bins sum to 1.0
  5. Match against chord formulas — same algorithm as fretboard detection

Same ChordDetector with different input — code reuse across features

The app can also detect chords from audio, not just from fretboard taps. The chromagram is a standard MIR technique. Take the FFT, map each frequency bin to one of 12 pitch classes, accumulate energy, normalize, and feed that into the same chord formula matcher.

Algorithmic Chord Voicings

Voicings are not stored — they are generated at runtime

  1. Given root + chord formula → required pitch classes
  2. Enumerate fret position combinations across 4 strings
  3. Filter: each string must contribute a required pitch class
  4. Rank by playability (spread, open strings, barre potential)
Adding a new chord formula automatically generates voicings for every root note
The chord library does not have a database of voicings. Given a root note and a chord formula, it enumerates combinations of fret positions across 4 strings, filters for valid combinations, and ranks by playability. Adding a new chord formula automatically generates its voicings — zero manual work.

Testing Strategy

LayerToolPurpose
Unit tests kotlin.test Domain logic, data models
Property-based Kotest Thousands of random inputs per test
Fuzz tests Jazzer Adversarial inputs: NaN, Infinity, huge buffers
  • CI: GitHub Actions on every push and PR
  • Coverage: 86.8% instruction coverage (Kover)
  • 39 test files in shared + 7 in app
Testing audio and music algorithms is tricky — edge cases are everywhere. I use three layers. Standard unit tests. Property-based tests with Kotest that verify invariants like transposing up then down returns the original. And fuzz tests with Jazzer that throw adversarial data to ensure nothing crashes.

Property-Based Testing

// Invariant: detect() never throws, regardless of input
@FuzzTest
fun fuzzDetect(data: FuzzedDataProvider) {
    val sampleRate = data.consumeInt(8_000, 192_000)
    val size = data.consumeInt(0, 16_384)
    val samples = FloatArray(size) {
        data.consumeFloat()  // NaN, Inf, denormals...
    }
    PitchDetector.detect(samples, sampleRate)
}

// Property: transpose(n) then transpose(-n) == identity
checkAll(Arb.int(0..11), Arb.int(-12..12)) { pc, n ->
    val result = transpose(transpose(pc, n), -n)
    result shouldBe pc
}
Here is what the tests look like. Jazzer generates structured random data. The fuzz test asserts that detect() does not throw. The property test verifies that transpose is its own inverse. These have found real bugs: denormalized floats, division by zero.

Accessibility: Not an Afterthought

Designed for blind and visually impaired musicians

  • TalkBack (Android) + VoiceOver (iOS) on every element
  • Heading semantics for screen reader navigation
  • Live regions: tuner readings announced in real time
  • Canvas components (tuner, fretboard, chord diagrams) have text alternatives
  • High-contrast theme + left-handed mode
"Breaking accessibility is treated as seriously as breaking functionality" — AGENTS.md
A core user base includes blind and visually impaired musicians. This is not a nice-to-have — it is a design constraint. Every code change must preserve accessibility. The tuner uses live regions so screen readers announce the detected note as it changes. The fretboard and chord diagrams have text alternatives.

Lessons Learned

  1. Push logic into the shared module — platform code handles platform APIs only
  2. Accessibility from day one — it's 10x harder to add later
  3. Offline-first is a feature, not a limitation — users trust what they control
  4. Property-based testing catches bugs humans would never write test cases for
  5. Parity is a product feature — not done when screens match, done when behavior is identical
Five lessons. First, maximize shared code. Second, accessibility from the start — I tried adding TalkBack after the fact once and it took three times as long. Third, I shipped cloud sync and then removed it. Fourth, property-based testing found real bugs. Fifth, iOS parity is ongoing work.
